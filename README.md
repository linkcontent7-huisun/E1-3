## 🧒 쉽게 말하면

> 컴퓨터는 사람처럼 **모양을 보지 못한다.** 그림을 숫자 칸으로 바꾸고, 같은 칸끼리 **곱해서 전부 더한 점수**로 "비슷한지"를 판단한다.
> 이 과제는 그 계산을 직접 손으로 짜 보는 체험이다. 코드는 `main.py` 한 파일이다.

이 과제에서 만나는 말 여섯 개만 그림으로 기억하면 된다.

| 말 | 비유 | 이 과제에서 |
|---|---|---|
| 🔲 **패턴** | 종이에 찍힌 **도장 자국** | 3×3 칸에 1(찍힘)과 0(빈칸)으로 적은 그림 |
| 🖋️ **필터** | 찾고 싶은 모양의 **도장 틀** | 십자가 틀(Cross), X 틀 |
| ✖️➕ **MAC** | 도장 틀을 종이 위에 **겹쳐 놓고, 같은 칸끼리 곱해서 전부 더하기** | 칸이 많아질수록 계산도 많아진다 |
| 🏆 **점수** | 겹쳐 본 뒤 나온 **일치도** | 점수가 높은 쪽 틀과 더 닮은 그림이다 |
| ⚖️ **허용오차** | 저울의 **눈금 오차**를 감안하는 규칙 | 0.9와 0.8999999…는 같은 값으로 본다 |
| 🏭 **NPU** | MAC 계산만 **엄청나게 빨리** 하도록 만든 AI 전용 칩 | 이 과제는 그 계산의 원리를 흉내 낸다 |


## 🧭 코드 지도

파일은 `main.py` 하나, 전부 **446줄**이다. 번호 순서대로 읽으면 된다.

| 번호 | 구역 | 하는 일 (비유) |
|---|---|---|
| 1 | `Grid` 클래스 | **도장 판.** n×n 칸에 숫자를 넣고, 꺼내고, 줄 목록으로 만든다 |

| 8 | 보너스 1 | 2차원 배열을 1차원으로 펼친 뒤 두 방식의 속도와 점수를 비교한다 |
| 9 | 보너스 2 | 십자가·X 패턴 생성기 |

### 핵심 계산 — MAC (main.py 일부)

```python
def mac(pattern, filt):
    score = 0.0
    for r in range(filt.size):              # 행을 하나씩
        for c in range(filt.size):          # 칸을 하나씩
            score += pattern.get(r, c) * filt.get(r, c)   # 같은 칸끼리 곱해서 더한다
    return score
```

**읽는 법:** 두 겹의 `for`가 칸을 전부 한 번씩 훑는다. 그래서 칸이 n×n이면 곱셈도 **n²번**이다. 이것이 뒤에 나오는 시간 복잡도 O(N²)의 이유다.

### 동점 판정 — 허용오차 (main.py 일부)

```python
EPSILON = 1e-9   # 두 점수의 차이가 이보다 작으면 같은 점수로 본다

def judge(score_a, score_b):
    if abs(score_a - score_b) < EPSILON:
        return "UNDECIDED"                  # 동점: 판정 불가
    return "A" if score_a > score_b else "B"
```

**읽는 법:** 컴퓨터의 소수 계산은 아주 조금 틀릴 수 있다. 그래서 "완전히 같은가"가 아니라 "차이가 아주 작은가"로 같은 점수를 정한다.

### 라벨 통일 (main.py 일부)

```python
def normalize_label(text):
    key = str(text).strip().lower()
    if key in ("+", "cross"):
        return CROSS          # "Cross"
    if key == "x":
        return X_LABEL        # "X"
    raise ValueError("알 수 없는 라벨: {!r}".format(text))
```

**읽는 법:** 같은 뜻을 여러 글자로 적어도 한 가지 이름으로 바꿔서 비교한다. 이름표가 달라서 틀리는 일을 막는다.

이 과제는 **그림의 모양을 숫자 계산으로 알아맞히는** 작은 시뮬레이터다. 실제 AI 칩(NPU)이 하는 계산 한 가지, MAC 연산을 흉내 낸다.

- 같은 커밋에 MAC, 허용오차 판정, 모드 1, 모드 2, 라벨 정규화, 성능 측정, 보너스 2종이 함께 들어 있다. **기능 단위로 나누지 못한 점은 아쉬움으로 남긴다.** (E1-2처럼 나눠 쓰려면 기능마다 따로 커밋했어야 했다.)
- 확인 1: 명세 예시 입력에서 A 1.0, B 5.0, 판정 B가 나왔다. ([로그 A](docs/logs/02-run-demo.md))
- 확인 2: `data.json` 6개 케이스 모두 판정·비교가 끝났다. 실패 3개의 원인은 [결과 리포트](#-결과-리포트)에 있다.

## 🧪 결과 리포트

### 1. 전체 결과 (data.json, 로그 C)

| 항목 | 값 |
|---|---|
| 총 테스트 | 6개 |
| 통과 | 3개 (size_5_2, size_13_1, size_25_2) |

### 2. 실패 원인 분석

실패 3개는 전부 **같은 종류**다. 두 점수가 **정확히 같은 수학적 동점**이라서 판정이 `UNDECIDED`(판정 불가)가 됐고, 명세 규칙대로 `UNDECIDED`는 expected와 다르니 FAIL이다.

| 케이스 | Cross 점수 | X 점수 | 정확한 값(분수 계산) | 기대값 | 원인 분류 |
|---|---|---|---|---|---|
| size_5_1 | 0.9 | 0.8999999999999999 | 둘 다 0.9 (동점) | X | 수치 비교 (동점) |
| size_13_2 | 7.499999999999997 | 7.5 | 둘 다 7.5 (동점) | Cross | 수치 비교 (동점) |
| size_25_1 | 4.9 | 4.899999999999999 | 둘 다 4.9 (동점) | X | 수치 비교 (동점) |

**진단을 세 갈래로 나눴다** (명세 요구: "데이터/스키마 vs 로직 vs 수치 비교"):
- **데이터/스키마 문제: 0건.** 6개 키가 모두 `size_N_번호` 형식이고, 필터와 패턴 크기가 키의 N과 모두 맞았고, 라벨도 모두 정규화되었다.
- **로직 문제: 0건.** MAC은 명세 예시(A 1.0, B 5.0)와 정확히 같고, 정확한 분수 계산과 비교해도 점수가 같았다.
- **수치 비교 문제: 3건.** 실제 값은 동점인데, 소수 계산 오차 때문에 점수가 0.9와 0.8999…처럼 조금씩 다르게 나온다. 그래서 허용오차 없이 `>`로만 비교하면 한쪽이 이긴 것으로 잘못 판정된다.

**허용오차를 빼면 어떻게 될까?** (실제로 확인한 값) 오차 때문에 size_5_1은 Cross, size_25_1은 Cross, size_13_2는 X가 이긴 것으로 나온다. 세 케이스 모두 여전히 FAIL이라 PASS/FAIL 개수는 같지만, **이유는 "잘못된 승자"로 바뀐다.** 허용오차는 "동점은 동점이라고 말하게" 해서 이유를 정확하게 만든다.

**남은 질문 ❓:** 명세 규칙으로는 동점을 FAIL로 두는 것이 맞다. 그러나 expected가 동점 케이스에 승자를 지정한 것은 데이터 작성 의도에 대한 질문이다. 이 질문은 ⏳ 확인하지 않았다. 교수자가 동점을 다르게 다루라고 한다면 `judge`의 규칙만 바꾸면 된다.

### 3. 시간 복잡도 — O(N²)

패턴이 n×n일 때 MAC 한 번은 칸 n²개를 한 번씩 곱하고 더한다. 측정 결과는 아래와 같다.

| 크기 (N×N) | 평균 시간 (ms, 10회) | 연산 횟수 (N²) |
|---|---|---|
| 3×3 | 0.0012 | 9 |
| 5×5 | 0.0023 | 25 |
| 13×13 | 0.0271 | 169 |
| 25×25 | 0.0489 | 625 |

*(로그 C 기준. 시간은 실행마다 달라진다.)*

**해석:**
- **연산 횟수는 N²과 정확히 맞는다.** 25×25는 3×3보다 625/9 ≈ 69배 많은 곱셈을 한다.
- **시간은 방향만 맞고 비율은 들쭉날쭉하다.** 같은 코드로 두 번 잰 13×13 값은 0.0185ms와 0.0271ms였다. 측정 시간이 1ms 아래로 아주 짧아서 함수 호출과 측정 오차의 영향이 크다. 그래서 시간만으로 N²의 비율을 정확히 확인하지는 못했다. ⏳ 더 많이 반복하거나 더 큰 N으로 재면 확인할 수 있다.
- **큰 N일수록 시간이 빠르게 늘어난다는 방향**은 표에서 분명하다. 연산 수가 N²으로 늘어나므로 필터가 수백 칸이면 곱셈이 수만 번이 되고, 이것이 NPU처럼 많은 곱셈을 **동시에** 하는 칩이 필요한 이유다.
- 결론: 연산 횟수 기준으로 O(N²)은 확인됐고, 시간 기준 O(N²)은 방향으로만 확인했다.

## 🔧 트러블슈팅

**1. 데이터 파일 다운로드가 `.tmp`로 멈춤**
- 문제: 코디세이에서 `data.json` 링크를 눌렀지만 다운로드 폴더에 `data.json`이 생기지 않았다. 대신 같은 내용의 임시 파일(`.tmp`, 약 20KB)이 남았다.
- 원인 가설: 브라우저가 다운로드를 끝냈지만 이름 바꾸기 단계에서 멈췄다.
- 확인: 임시 파일을 JSON으로 읽어 보니 `meta`·`filters`·`patterns`가 명세 구조와 맞았고 파일 크기도 더 자라지 않았다.
- 해결: 내용을 검사한 뒤 `data.json`이라는 이름으로 복사했다. 이 복사본은 원본과 해시 비교를 하지 않았다(⏳). 파일 검사 명령은 이 README 본문에 적은 확인 결과를 근거로 한다. (별도 로그는 없다)

**2. 테스트 출력에서 한글이 깨짐**
- 문제: 검사용 스크립트를 파이프로 실행하자 한글 오류 문구가 깨져 보였다.
- 원인 가설: 한글 Windows의 파이프 출력 인코딩(cp949)이 기본값이었다.
- 확인: `PYTHONIOENCODING=utf-8`을 붙이자 정상 출력됐다. 같은 현상이 `main.py`에는 없다(`use_utf8_io()`로 이미 UTF-8 설정).
- 해결: 검사 스크립트 실행 시 인코딩을 지정했다. 프로그램 코드는 바꾸지 않았다.

**3. 명세 예시와 실제 데이터 개수가 다름**
- 문제: 명세 예시는 8개 케이스지만 `data.json`은 6개다.
- 원인 가설: 예시는 참고용이라 실제 파일과 다를 수 있다.
- 확인: 파일을 직접 세어 보니 6개다. 명세에도 "정답이 아니라 참고 예시"라고 적혀 있다.
- 해결: 코드는 파일이 가진 만큼 전부 판정한다. README의 총 테스트 수도 6개로 적었다.

| 말 | 쉬운 뜻 |
|---|---|
| 패턴 | 판정할 그림 (칸마다 1 또는 0) |
| 필터 | 찾고 싶은 모양의 틀 |

| 시간 복잡도 O(N²) | 칸이 n×n이면 계산이 n²에 비례해서 늘어난다는 뜻 |
| NPU | AI 계산(MAC)만 빠르게 많이 하도록 만든 칩 |
